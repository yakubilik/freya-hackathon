# R1: forward reading of a bank brief into a rule table

You compile one bank's call brief into a rule table: canonical JSON in a brief-agnostic schema. Everything
downstream (the test oracle, the agent generator, the scorer) reads only your table, never the brief. What you
leave out does not exist; what you invent is a verified failure. Work from the text in front of you only. Use
nothing you remember about other briefs, other banks or how collections calls usually go. Where the brief is
silent, say so explicitly: the string `NOT SPECIFIED` in free-text fields, `"confidence": "not_specified"` with
no `value` in parameter entries. Never fill a gap with a plausible default.

## Inputs

1. `documents`: the brief split into documents (a brief, a mail, a memo, a dated section). You decide each
   document's `role`: `authoritative` (the operative specification), `amends` (changes clauses of another
   document with authority language), `informational` (no operative content), `superseded` (replaced by a
   later document that says so). Chronology alone is not authority: a later document revokes an earlier one
   only where it says so. A memo that states a different value without amendment language is an `inferred`
   amendment and must also appear in `open_questions`.
2. `units`: every unit of the brief with its id, kind and exact text (lossless segmentation: sentences,
   table rows, headings, list items, blockquote lines, footnotes, `other` for markup such as table separator
   rows and fences). You cite unit ids. Every quote you store must be a verbatim substring of the cited
   unit's text (whitespace may differ, nothing else).
3. `api`: the tool API, already parsed into `wire_map.tools` (tool names, paths, methods, request and
   response fields with their enums). Write `wire_map.tools` as `{}`; code inserts the parsed API after your reply. Tool names, field names and
   enum values are exact wire strings: no case folding, no renaming, no numeric conversion. Where the API
   defines an enum, the API is the authority for the spelling; where it leaves a field free (a free string
   reason, for example), the brief's own table or code list is the authority.
4. `schema`: the JSON Schema your `table` must satisfy. `additionalProperties` is false almost everywhere.

## Output contract

Return exactly one JSON object and nothing else (no prose, no code fence). Write `table` first, then
`question_battery`, then `reader_notes`, so a truncated reply loses the battery, not the table:

```
{"table": <rule_table conforming to the schema>,
 "question_battery": [{"n": 1, "question": "...", "answer": "...", "units": ["d1.s8"]}, ... all 40 ...],
 "reader_notes": "anything the schema could not hold, in a few lines"}
```

## The table, field by field

**documents[]**: `{doc_id, kind, title, issue_date, role, evidence_units}`. `issue_date` ISO or null.
`evidence_units`: the units that establish the role (a `Subject:` line, "is replaced by", a date line).

**units**: write `{}`. Code inserts the segmenter's units after your reply; cite their ids everywhere.

**dispositions**: one entry for EVERY unit id, including headings, table header rows, separator rows (`other`
units are `informational` with reason `markup`) and introductory sentences. Kinds: `obligation` (with `refs`
listing the obligation ids drawn from it; every obligation unit needs at least one), `definition` (defines a
term, a floor, a band, a calendar; `refs` may list obligations that use it), `example` (a worked example;
add it to `examples[]`), `informational` (no operative content; give the `reason`), `superseded` (give the
`evidence` unit that supersedes it), `unreadable`. A sentence with an operative verb (say, ask, call, close,
do not, never, must, offer, propose, treat as, counts as) is an obligation unit, not informational.

**obligations[]**: one atomic obligation per rule, `id` = `O-<unit>.<n>` (for example `O-d1.s41.1`), `units`
the ids it rests on, `quote` verbatim from those units. `when`: `state` from
`pre_verification, identity, verified, third_party, disclosure, negotiation, readback, recording, closing, any`;
`guards` as expressions over `product.*`, `customer.*`, `call.*` and engine state (for example
`product.band == 'late'`, `attempts_used == 1`, `identity.wrong == 3`); `event` from
`party_confirmed, party_other, party_wrong_number, party_deceased, id_answer, id_decline, question_back, callback_offer,
pay_today_yes, pay_today_no, date_proposal, amount_proposal, too_much, refuse, accept_offer, vague_period, confirm, deny,
change, paid, dispute, plan_request, human, hardship, scam_question, robot_question, dont_want_to_talk, tool_result, other`,
or `customer.<free text>` for something the engine does not model (then set `capability` to `prompt_only`).
`then`: a list of single-key actions from `say{exact|content}`, `ask{question_id|content}`,
`offer{amount_rule, date_expr, once}`, `tool{name, args}`, `close{outcome, reason}`, `forbid: "<what>"`,
`transfer{queue}`, `note{reason, text}`, `callback{}`, `defer: "<what>"`, `count{counter, max}`, `stop: true`,
`other: "<text>"`. `kind`: `state | communication | ordering | prohibition | definition`. `scope`: `call`,
`product` or `document:<doc_id>`. `status`: `effective | superseded | informational`.

Rules for obligations:
- An exception is its own obligation with `exception_of` set to the general obligation's id and its scope
  condition in `guards`. "unless", "except", "only", "existing", "new", "still", "even if" are signals.
- A rule that says it comes before another rule gets `precedence: ["before O-..."]` on the winning side.
- A mandatory sentence gets `say.exact` with the exact words and a `phrases[]` entry. A forbidden word or
  sentence gets `forbid` and a `phrases[]` entry with `kind: forbidden` and a `when` that says until when.
- Each close instruction gets `close{outcome, reason}` with the exact wire strings; `reason` null when the
  closing table lists none.
- Each tool instruction gets `tool{name, args}` with the API's tool name and field names; use `{{var}}` style
  placeholders for values that come from the call (`{{customer_id}}`, `{{product_id}}`).
- Counting rules (`once`, `twice`, `three`, `one more`) get `count{counter, max}` next to the action.
- Rules with effective dates get `effective{from, to, anchor, inclusive}`; `anchor` is `call_date`,
  `product.<field>` or `agreement_date`, never implied.
- Do not merge two rules into one obligation; do not split one sentence into obligations that repeat each
  other. A worked example ("So 'next Friday' said on a Friday is ...") is `examples[]`, not an obligation.

**parameters**: dotted path to `{value | windows[], type, quotes[], units[], obligations[], confidence}`.
`confidence`: `quoted` (the value is in the text), `derived` (computed from the text, say how in `quotes`),
`not_specified` (silent; no `value`). Well-known paths, each present, as a value or as `not_specified`:
`party.confirmation_words` (list), `party.non_confirmation_words`, `party.max_asks`,
`third_party.callback.window` `{days_expr, start, end, inclusive}`,
`identity.questions` (list of `{id, wire_field, type: date|digits:N|year|text, parse_rule, order}`),
`identity.max_wrong`, `identity.hint_rule`, `identity.decline_rule`,
`calendar.holidays` (ISO dates), `calendar.business_days` (list of weekday names),
`bands` (list of `{id, condition, deadline_expr, attempts}` with `condition` over `product.<response field>` and
`deadline_expr` in the expression language),
`dates.vague_rule`, `dates.this_next_rule`, `dates.bare_weekday_rule`, `dates.after_deadline_rule`, `dates.weekend_holiday_rule`,
`amounts.floor_expr` (one expression per product type, for example
`product.<field> if product.type == '<type>' else product.<other field>`; the language has no `?:`),
`amounts.range_rule`, `amounts.first_ask`, `attempts` (list of `{n, amount_rule, date_expr, band}`),
`situations` (object with keys `hardship, paid, dispute, plan_request, human, scam, robot, deceased, wrong_number, dont_want_to_talk`,
each `{obligations[], outcome, reason, queue}` or `NOT SPECIFIED`),
`recording.retries`, `recording.success_sentence`, `multi.max_items`, `multi.order`,
`closing.rows` (list of `{outcome, reason, triggers: [engine trigger names], precedence, obligations: [obligation ids], units}`;
`reason` null for none; one row per outcome/reason pair; see the engine contract), `call_variables` (list of `{name, meaning}`), `opening.sentence_content`,
`opening.right_party_question`, `disclosure.content`.

**Expression language** (the only syntax allowed in `*_expr`, `condition` and `offer.date_expr`):
arithmetic, `min`, `max`, `round(x, step, mode)`, `a if cond else b`, fields of `product`, `customer`, `call`; `today`,
`tomorrow`, `now`, `deadline`, `deadline - n`, `business_days_after(anchor, n)`, `calendar_days_after(anchor, n)`,
`next_business_day(d)`, `on_or_next_business_day(d)`, `this_weekday(w)`, `next_weekday(w)`,
`last_business_day_of_week(d)`, `last_business_day_of_next_week(d)`, `end_of_month(d)`,
`in_window(t, start, end, inclusive)`; comparisons `== != < <= > >=`, `and`, `or`, `not`; string literals in
single quotes. The calendar is named `default`. Example: deadline of a band "the 7th business day after
today" is `business_days_after(today, 7)`; "the last business day of this week, or of next week if today is
that day" is `last_business_day_of_week(today) if last_business_day_of_week(today) != today else last_business_day_of_next_week(today)`.

**amendments[]**: `{amending_unit, amended_units, path, old, new, authority, issue_date, effective, scope, quotes}`.
`authority`: `explicit_replaces` ("is replaced by"), `explicit_effective_date` ("effective from"),
`stated_supersession` ("supersedes"), `inferred` (a different value with no amendment language). An amendment
with an effective date needs `effective: {from, to, anchor, inclusive}`. Empty list when there is none.

**wire_map**: `tools` copied from the input. `concepts`: at least `close_outcome`, `close_reason`,
`transfer_queue`, `note_reason`, `identity_field`, `identity_answer`, `account_lookup`, `promise_record`,
`callback`, `close`, `transfer`, `note`, each `{tool, field, wire, units}` (`wire` is the exact field or
value, `field` may be `""` for a tool-level concept). `enums`: one key per API enum value as
`tool.field.value` (for example `close_call.outcome.promise`) mapping to `{obligations: [...]}` or
`{unused: "<reason from the brief>"}`; also one key per brief code the API cannot carry.

**phrases[]**: `{id, kind: mandatory|forbidden, text, exact, obligation, when}`; `exact` true when the brief
gives the words in quotes.

**examples[]**: `{unit, input, expected}` for every worked example in the brief.

**open_questions[]**: `{topic, readings[], taken, rule}` for every place where two readings are possible;
`rule` names which of these chose: (1) authority and applicability evidence beats none; (2) explicit beats
inferred; (3) narrower scope beats general; (4) later issue date among qualifying documents; (5) the
auditor's source reading; (6) the reading that forbids more.

**plan[]**: the order of stages, each `{id, type, params, obligations[], units[], per_item, gates[]}`.
Vocabulary, one line each:
- `party`: reach the right person (confirmation words, asks, third-party branch, wrong number, deceased).
- `verify`: the identity questions; `gates` lists the stage ids that may not run until it passes.
- `consent`: an explicit consent question the brief requires before something.
- `say`: a mandatory sentence at a fixed point (opening sentence, recorded sentence).
- `ask`: a mandatory question at a fixed point that is not part of another stage.
- `fetch`: the account lookup tool call.
- `disclose`: state the debt (team, product, amount, days late).
- `negotiate`: the first ask, the amount and date rules, the persuasion attempts.
- `readback`: read the promise back and ask the confirmation question.
- `record`: the promise tool call with retries.
- `note`: the note tool call for products without a promise.
- `close`: thanks, goodbye, the close tool call.
- `prompt_only`: an obligation at a fixed point that no other type carries (rendered as prompt text).
Default plan: `party, verify, fetch, disclose, negotiate, readback, record, note, close`. Rules: an inserted,
moved or repeated stage needs at least one unit whose quote states that step or that order (put it in
`units`); a default stage is omitted when no obligation maps to it (Brief A has no note stage, for example);
`per_item: true` for stages that run once per product; the first `verify` comes before `fetch`, `disclose`,
`record`; `close` is last. Put the ids of the obligations each stage realises in `obligations`.

## Question battery

Use the 40 questions below as your reading checklist; answer each in `question_battery` in one short line
with the unit ids it rests on, or "the brief is silent". Where a memo changes a rule, quote the latest text and name what it replaces.

**Scope and inputs**
1. Who is called, about what (product types / [I] policy types), and how late or how close to lapse/renewal?
2. Which call variables exist before any tool call, and which one is "now"? Is the real clock forbidden?
3. Which tools exist, which fields and enum values changed, and which tool is refused until which condition?
4. Is there a code list / outcome table? List every outcome + reason and the rule that triggers each.

**Opening and right party**
5. What must the first sentence contain (organisation, automated-assistant status, recording notice, agent name)? Which words are forbidden in it and until when?
6. How is the customer addressed, and what is the exact right-party question?
7. What counts as a confirmation, what does not, how many asks, and what closes an unclear call?
8. What does the agent say when asked if it is a robot/AI? When asked if it is a scam?

**Third parties**
9. What may be said to a non-customer? Does it differ for a relative, a spouse, an authorised representative / [I] named driver, beneficiary, broker?
10. Callback: allowed days, hours (inclusive?), relation to "now", how many retries, what if no time is given?
11. Wrong number, deceased: exact words, what else is forbidden, which outcome?

**Identity**
12. Which questions, in which order, one at a time? Which formats must be sent to the tool (date order, digits)?
13. How many wrong answers in total or per question? Any hint (e.g. swapped day/month) that does not count?
14. What if the customer declines, or asks the purpose instead of answering? How many times is the reason explained?
15. What is said after failure (alternative channel), and what must not be said?

**Stating the obligation**
16. What must be said once verified (team name, "late payment", [I] "premium unpaid", lapse/grace date)? How is each product/policy named?
17. With several products/policies: all stated first? Order? One sentence each?

**Dates and amounts**
18. Calendar: business days, holidays, time zone, cut-off times. Is today allowed?
19. Deadline per band / product / [I] grace period end; bands by which field; inclusive edges?
20. Rules for weekend/holiday dates, vague periods, "this/next <weekday>", dates after the deadline.
21. Amount ladder: full first? floor field per product type? accepted range (inclusive)? below-floor and above-full handling? Does the agent or the customer propose amounts? "How much can you pay" ban?
22. [I] Partial premium accepted? Does paying restore cover at once or after a reinstatement step? Any fee or interest to state?

**Persuasion and offers**
23. What is the first ask, verbatim? How many persuasion attempts per band/product, and what does each propose?
24. What counts as a refusal, a non-answer, a counter-proposal? When to stop? Repeat bans?
25. Which offers are forbidden (discount, waiver, plan, [I] cover change, premium reduction, advice on switching)? Which offers or routes are allowed?

**Confirmation and recording**
26. Read-back content, exact confirmation question, what counts as yes, what happens on a change at the read-back?
27. Order of tool calls (one per product? all after one confirmation?), retries on failure, what is said on success and on failure, exact post-success sentence (text/letter/email)?
28. Can a recorded promise be changed or cancelled in the call? Where can it be changed?

**Customer situations**
29. Hardship / vulnerability triggers (illness, bereavement, job loss, [I] accident, hospitalisation): exact response, sentence count, persuasion ban, referral queue, outcome if declined, precedence over other rules?
30. "Already paid": exact sentence, scope (this amount only?), outcome or note.
31. Dispute: what counts (not mine, closed, paid off earlier, [I] "I cancelled the policy", "the claim was rejected unfairly")? What is forbidden (arguing, promise)? Outcome/note?
32. Restructuring / new plan / [I] change of cover or payment frequency: route, queue, what happens to agreed and recorded promises, notes?
33. Request for a human: help-first ask? queue? Refusal to talk: how many times, outcome before and after ID&V?
34. Questions the tools cannot answer: exact fallback; [I] claim outcomes, cover questions, medical details.
35. Complaints, bankruptcy, legal representation, language needs, cease-contact requests: does the brief say anything? (Absent in A/B.)

**Closing and records**
36. Exactly one close call? Last tool call? Outcome precedence (promise vs transfer vs paid vs no_promise), multi-product reason order?
37. Notes: when, per product, which reasons, banned on which paths? Callback / transfer bookkeeping?
38. Closing courtesy: thanks and goodbye before closing?

**Literal-risk sweep (run after 1–38)**
39. List every word the brief forbids or time-gates, and every sentence it mandates. For each pair, does a mandated sentence contain a forbidden or gated word?
40. List every "once / one / exactly / at most / never" in the brief. Which natural agent behaviours would repeat it (re-offer, second sympathy, closing reminder)?

## Checks your table will face (write it to pass them)

- JSON Schema validation. Every quote verified as a substring of its units. Every unit dispositioned.
- Every `close.outcome`, `transfer.queue`, `note.reason`, `identity.questions[].wire_field` checked against
  the API enums; every `close{outcome, reason}` pair present in `closing.rows`; every closing row with a
  non-empty `triggers` list of engine trigger names and a non-empty `obligations` list of existing obligation ids.
- Every expression parsed; band conditions only over fields that exist in the lookup tool's response.
- Amendments with authority and anchored effective windows.
- Plan: vocabulary, one `party` first, one `close` last, first `verify` before `fetch`/`disclose`/`record`,
  cited units for every insertion, move or repeat.

Be complete rather than brief. A 45-rule brief yields roughly 60 to 110 obligations. Read every unit.

The engine contract that follows is part of these instructions: where it is more specific than the
field-by-field text above, follow the engine contract.
